# Why AI Breaks Differently

It's Tuesday morning. The same model that passed every test on Friday is suddenly returning worse answers. Nothing in the code changed. Nothing in the model changed. The world changed — and your system didn't notice. Welcome to the AI version of the Friday Night Problem, where 'it worked yesterday' is no longer a defense.

---

## Remember

AI systems differ from traditional software in four ways that matter for system design: **non-determinism** (the same input can produce different outputs), **marginal cost** (every request costs money), **data drift** (the world changes but the model doesn't), and **evaluation difficulty** ('it sounds right' isn't a metric). These four properties shape every architectural decision in the rest of this curriculum.

---

## Understand

Traditional software is deterministic: the same input always produces the same output. This makes it testable, debuggable, and predictable. AI systems are probabilistic: the same input can produce different outputs on different runs, depending on temperature settings, model version, and even the order of requests in a batch. This breaks traditional testing approaches — you can't assert `assertEqual(model.predict(x), y)` when the model might return a slightly different `y` each time.

The cost structure is also fundamentally different. Traditional software has fixed costs (servers) and near-zero marginal costs (one more user costs almost nothing). AI systems have variable costs that scale with usage — every request consumes tokens, every token costs money. A free tier that costs $0.01/user/month in traditional SaaS can cost $5–$50/user/month in an AI product.

Data drift is the silent killer. The model was trained on data from a specific point in time. The world moves on. User behavior shifts. New content appears. The model's accuracy degrades — not because it broke, but because reality diverged from its training data. Traditional software doesn't have this problem; code doesn't 'go stale' the way models do.

Evaluation is the hardest part. For traditional software, you write tests: input X should produce output Y. For AI, what's the 'correct' answer to 'write a summary of this article'? Multiple valid answers exist, quality is subjective, and ground truth is expensive to obtain. 'It sounds right' is not an evaluation — but it's what most teams ship with.

---

## Apply

Take any AI system you've used recently — a chatbot, a recommendation feed, a search engine. For each of the four properties above, identify one specific way it manifests:

1. **Non-determinism**: Have you ever asked a chatbot the same question twice and gotten different answers? That's non-determinism.
2. **Marginal cost**: If you use an AI tool heavily, do you hit rate limits? That's the provider protecting their margin.
3. **Data drift**: Have you noticed search results getting worse over time, or recommendations feeling stale? That's drift.
4. **Evaluation difficulty**: Have you ever been unable to tell if an AI's answer was good or just confident? That's the eval problem.

---

## Analyze

These four properties interact and compound. Non-determinism makes evaluation harder (how do you test something that gives different answers?). Data drift makes non-determinism worse (the model's behavior shifts over time, in ways you didn't intend). Marginal cost makes data drift expensive (you can't just retrain on every request to fix drift — it costs too much). The interactions are why AI system design is a distinct discipline, not just 'software design with models.'

---

## Evaluate

When designing an AI system, ask: which of these four properties is most dangerous for my use case? A medical diagnosis system cares most about evaluation (false confidence is dangerous). A recommendation system cares most about drift (stale recommendations lose users). A free-tier chatbot cares most about cost (abuse is existential). A coding agent cares most about non-determinism (the same task should produce a working fix, not a random one). Prioritize your defenses accordingly.

---

## Create

Sketch the four-property profile for a system you'd want to build. For each property, write one sentence on how you'd defend against it. This profile becomes the design constraints that shape every subsequent decision.

---

## A common misconception

**'AI is just software with models in it.'** No. The four properties above aren't features of the model — they're properties of the *system*. A system that happens to call an LLM but treats it like a deterministic database lookup will fail in production. A system designed around non-determinism, cost, drift, and evaluation will survive. The model is one component; the system design is what makes it work.
