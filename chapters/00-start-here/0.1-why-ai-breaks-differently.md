# Why AI Breaks Differently

It's Tuesday morning. The same model that passed every test on Friday is suddenly returning worse answers. Nothing in the code changed. Nothing in the model changed. The world changed — and your system didn't notice.

The data science team swears nothing changed. They're right — and wrong. Nothing in the *code* changed. But the *world* did. A competitor launched a new feature. User behavior shifted. The data the model was trained on stopped representing reality. The model didn't break — reality drifted away from it.

Welcome to the AI version of the Friday Night Problem, where "it worked yesterday" is no longer a defense. Traditional software is deterministic: the same input always produces the same output. AI systems are probabilistic: the same input can produce different outputs, and the "correct" output changes over time. This breaks traditional testing, debugging, and reliability practices.

This chapter is about the four properties that make AI systems fundamentally harder to design than traditional software — and the defenses you build for each.

---

## Remember — name it

AI systems differ from traditional software in four ways that matter for system design:

1. **Non-determinism** — the same input can produce different outputs. Run the same prompt through GPT-4o twice; you may get different answers. This breaks `assertEqual(model.predict(x), y)` — you can't assert exact equality when the output varies.
2. **Marginal cost** — every request costs money. Traditional software has near-zero marginal cost (one more user costs nothing in server time). AI systems pay per token — every request consumes compute that costs real money.
3. **Data drift** — the world changes, the model doesn't, until you retrain. A recommendation model trained on January data is stale by March. Traditional code doesn't "go stale" — `2 + 2 = 4` is forever. Models degrade silently.
4. **Evaluation difficulty** — "it sounds right" isn't a metric. For traditional software, you write tests: input X should produce output Y. For AI, what's the "correct" answer to "write a summary of this article"? Multiple valid answers exist, quality is subjective, and ground truth is expensive to obtain.

Each of these requires a different defense. We'll cover them in the Apply section.

## Understand — explain it in plain words

### Non-determinism

Traditional software is deterministic: `add(2, 3)` always returns `5`. This makes it testable, debuggable, and predictable. You can write unit tests that assert exact outputs. You can reproduce bugs by replaying the input.

AI systems are probabilistic. The same prompt to an LLM can produce different outputs on different runs, depending on:
- **Temperature** — a parameter that controls randomness. Temperature 0 makes the model deterministic (it always picks the highest-probability token). Temperature 1 introduces randomness. Most production systems use temperature 0-0.3 for consistency, but even at temperature 0, different model versions or batch sizes can produce different outputs.
- **Model version** — OpenAI silently updates models. `gpt-4o-2024-08-06` and `gpt-4o-2024-11-20` may give different answers to the same prompt. This breaks reproducibility.
- **Floating-point non-determinism** — GPU computations are not bit-reproducible across different hardware. The same model on different GPUs can produce slightly different outputs.

This breaks traditional testing. You can't assert `assertEqual(model.generate("What is 2+2?"), "4")` when the model might output "4", "The answer is 4", "2 + 2 = 4", or "Four". The fix: test for *properties* (does the answer contain "4"? is it less than 100 characters? does it not contain harmful content?) rather than exact strings.

### Marginal cost

Traditional software has fixed costs (servers) and near-zero marginal costs. One more user costs almost nothing — the server is already running. This is why SaaS could scale to millions of free users: the cost per user was negligible.

AI systems have variable costs that scale with usage. Every LLM call costs money — you pay per token (input and output). A single user sending 1,000 messages a day can cost $50/month in token costs alone. This is the AI startup death spiral: if your cost-per-request is $0.05 and your revenue-per-request is $0.03, more users means you lose money faster.

Real numbers (as of August 2026):
- Claude 3.5 Sonnet: $3/1M input tokens, $15/1M output tokens
- GPT-4o: $2.50/1M input, $10/1M output
- GPT-4o-mini: $0.15/1M input, $0.60/1M output (16x cheaper)
- Gemini 1.5 Flash: $0.075/1M input, $0.30/1M output (40x cheaper)

A typical RAG query with 2,000 input tokens and 300 output tokens costs:
- With Sonnet: (2000 × $3/1M) + (300 × $15/1M) = $0.006 + $0.0045 = $0.0105
- With GPT-4o-mini: (2000 × $0.15/1M) + (300 × $0.60/1M) = $0.0003 + $0.00018 = $0.00048

At 10,000 queries/day, that's $105/day (Sonnet) vs $4.80/day (GPT-4o-mini). The 22x cost difference is why model routing matters (see chapter X.4).

### Data drift

The model was trained on data from a specific point in time. The world moves on. User behavior shifts. New content appears. The model's accuracy degrades — not because it broke, but because reality diverged from its training data.

There are two types of drift:
- **Data drift (covariate shift)** — the input distribution changes. Users who used to search for "iPhone 14" now search for "iPhone 16". The model still works, but it's answering yesterday's questions.
- **Concept drift** — the relationship between inputs and outputs changes. What was "good" content yesterday isn't "good" today. A fraud model trained on 2023 fraud patterns won't catch 2026 fraud patterns — fraudsters adapt.

Drift is silent. The model doesn't report "I'm degraded." It keeps producing outputs, just worse ones. You only notice when business metrics drop — engagement, conversion, click-through rate. By then, the drift has been happening for weeks.

### Evaluation difficulty

For traditional software, you write tests: `assertEqual(sort([3,1,2]), [1,2,3])`. The test passes or fails. There's a clear ground truth.

For AI, what's the "correct" answer to "summarize this article"? Multiple valid summaries exist. Quality is subjective. Ground truth requires human judgment, which is expensive ($1-10 per evaluation) and slow (days to weeks).

This is why "it sounds right" is the most common — and most dangerous — evaluation method. The Air Canada chatbot (2024) sounded right when it told a customer they could get a bereavement refund. It was wrong. The customer sued. Air Canada lost. "Sounds right" cost them real money.

The fix: structured evaluation with multiple dimensions (factuality, helpfulness, safety, tone), automated where possible (LLM-as-judge), calibrated against human eval, and run continuously in production — not just at launch.

## Apply — design defenses for each property

### Defense 1: Non-determinism → Property-based testing + reproducibility

Instead of testing exact outputs, test *properties*:
```python
# Bad: exact match
assert model.generate("What is 2+2?") == "4"

# Good: property-based
answer = model.generate("What is 2+2?")
assert "4" in answer  # contains the right number
assert len(answer) < 100  # isn't too verbose
assert "error" not in answer.lower()  # didn't error
```

For reproducibility, pin model versions: use `gpt-4o-2024-08-06` (specific snapshot) not `gpt-4o` (latest, changes silently). Log the model version with every request so you can reproduce issues.

### Defense 2: Marginal cost → Caching + routing + budgets

- **Prompt caching** — Anthropic and OpenAI cache prompt prefixes at 80-90% discount. If your system prompt is 4,000 tokens and stable, you pay 10% of full price for it.
- **Semantic caching** — cache answers to similar questions. 40-60% of customer support queries are repeats.
- **Model routing** — send easy requests to cheap models (GPT-4o-mini), hard requests to frontier models (Sonnet). 70-80% of requests can use the cheap model.
- **Hard budgets** — per-user, per-request, per-day limits enforced by the orchestrator. "Max $5/user/day" prevents abuse.

See chapter X.4 for the full cost optimization framework.

### Defense 3: Data drift → Monitoring + retraining

Monitor for drift:
- **Input distribution** — track feature statistics over time. Alert when they shift significantly (KL divergence, population stability index).
- **Output distribution** — track prediction statistics. If the model suddenly predicts more "positive" outcomes, something changed.
- **Ground-truth latency** — how quickly do you learn whether predictions were right? For ads, seconds. For loan defaults, months. Long latency means slow drift detection.
- **Business metrics** — the ultimate signal. If engagement drops, something is wrong — even if model metrics look fine.

Retrain when drift is detected:
- **Shadow deployment** — train new model, run it in parallel (not serving traffic), compare outputs. If better, promote.
- **Champion/challenger** — always have a challenger running. Don't wait for drift to retrain.

See chapter A.7 for the full retraining pattern.

### Defense 4: Evaluation difficulty → Multi-dimensional eval + regression suites

Build an evaluation pipeline:
- **Regression suite** — 50-500 test queries with known-good answers. Run on every change. If any test case gets worse, block the deploy.
- **LLM-as-judge** — a frontier LLM grades outputs of a smaller LLM. Cheap, fast, but biased (the judge may prefer outputs from similar models). Calibrate against human eval.
- **Human evaluation** — the gold standard. 50 random outputs per week, rated by humans. Calibrate the LLM-as-judge against this.
- **Production monitoring** — track user feedback (thumbs up/down), escalation rate (how often users ask for a human), resolution rate.

See chapter B.8 for the full GenAI evaluation framework.

## Analyze — how the four properties interact

These four properties don't exist in isolation. They interact and compound:

- **Non-determinism makes evaluation harder** — how do you test something that gives different answers each time? You test properties, not exact outputs.
- **Data drift makes non-determinism worse** — the model's behavior shifts over time, in ways you didn't intend. A model that was deterministic at launch becomes non-deterministic as the input distribution shifts.
- **Marginal cost makes data drift expensive** — you can't just retrain on every request to fix drift (it costs too much). You need a retraining pipeline that triggers on drift detection, not on every request.
- **Evaluation difficulty makes drift invisible** — if you can't measure quality, you can't detect drift. The model degrades silently until business metrics drop.

The interactions are why AI system design is a distinct discipline, not just "software design with models." A system that treats an LLM like a deterministic database lookup will fail in production. A system designed around non-determinism, cost, drift, and evaluation will survive.

## Evaluate — which property is most dangerous for your use case?

When designing an AI system, ask: which of the four properties is most dangerous for *my* use case?

- **Medical diagnosis** — evaluation is most dangerous (false confidence is harmful). Defense: human-in-the-loop for all diagnoses, confidence thresholds, refusal to answer when uncertain.
- **Recommendation feed** — drift is most dangerous (stale recommendations lose users). Defense: daily retraining, drift monitoring, explore/exploit balance.
- **Free-tier chatbot** — cost is most dangerous (abuse is existential). Defense: per-user rate limits, semantic caching, model routing to cheap models.
- **Coding agent** — non-determinism is most dangerous (the same task should produce a working fix, not a random one). Defense: temperature 0, deterministic tool execution, regression test suite.
- **Legal research** — evaluation and factuality are most dangerous (wrong advice has legal consequences). Defense: citations for every claim, refusal to answer when uncertain, human review for high-stakes queries.

Prioritize your defenses accordingly. You can't defend equally against all four — you have limited engineering time. Pick the one that's most dangerous for your use case and invest there first.

## Create — profile your system

Take any AI system you're building (or want to build). For each of the four properties:

1. **Non-determinism** — How would your system behave if the same input produced different outputs? What breaks? What's your defense (property-based testing, temperature 0, pinned model versions)?
2. **Marginal cost** — What's your cost-per-request? What's your revenue-per-request? Are they sustainable? What's your defense (caching, routing, budgets)?
3. **Data drift** — How quickly does your data go stale? What's your drift detection signal? What's your retraining cadence?
4. **Evaluation** — How do you know your system is good? What's your eval suite? How often do you run it?

Write one paragraph per property. This profile becomes the design constraints that shape every subsequent decision in this curriculum.

## A common misconception

**"AI is just software with models in it."**

No. The four properties above aren't features of the model — they're properties of the *system*. A system that happens to call an LLM but treats it like a deterministic database lookup will fail in production. A system designed around non-determinism, cost, drift, and evaluation will survive.

The model is one component; the system design is what makes it work. This is why MLOps exists as a discipline separate from DevOps — the operational challenges are fundamentally different.
