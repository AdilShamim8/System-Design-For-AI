# Six Words That Unlock Everything

Every craft has its six words. Cooking has 'salt, fat, acid, heat.' Music has 'melody, harmony, rhythm, timbre.' System design has its own six — and once you own them, every conversation about AI architecture stops sounding like a foreign language.

---

## Remember

The six words: **client**, **server**, **request**, **response**, **latency**, **throughput**. Two more that complete the starter kit: **scaling** and **tradeoff**. These eight words are the floor — everything else in the curriculum builds on them.

---

## Understand

**Client and server.** The asker and the answerer. Your browser is a client. The computer in a data center answering its requests is a server. In a restaurant: you're the client, the kitchen is the server. This seems simple, but the distinction matters because it determines who initiates communication (the client) and who responds (the server).

**Request and response.** The atomic unit of all client-server communication. One question, one answer. Everything else is built on this. When you load a webpage, your browser makes dozens of request-response pairs: one for the HTML, one for each CSS file, one for each image, one for each API call. Understanding this lets you reason about *what* a system is doing at any moment.

**Latency vs. throughput.** The two axes of performance, often confused. *Latency* is how long one request takes, measured in milliseconds. *Throughput* is how many requests happen per unit of time, measured in requests per second. They're related but not the same. A kitchen that handles 1,000 orders an hour but each takes 45 minutes has high throughput, high latency. A kitchen that handles 10 orders an hour but each takes 5 minutes has low throughput, low latency. You can optimize one and hurt the other — adding more chefs increases throughput but if they get in each other's way, latency per dish can increase.

**Scaling.** Making a system handle more load. *Vertical scaling* = buy a bigger server (one chef who's really fast). *Horizontal scaling* = add more servers (twenty regular chefs). Horizontal is cheaper and more reliable, but harder to design for — because now your servers need to coordinate, and coordination is where distributed systems get complex.

**Tradeoffs.** The central act of system design. You can't have everything — fast, cheap, reliable, pick two. Every design decision gives something up. System design is the art of choosing which things to give up.

---

## Apply

Take any app you used today. Identify: the client (your phone? your browser?), the server (where is it running?), one request-response pair you triggered (tapping a button → seeing a result). Estimate the latency (did it feel instant, or laggy?). This exercise makes the vocabulary concrete.

---

## Analyze

Latency and throughput are in tension. To increase throughput, you might batch requests — but batching adds latency (you wait for the batch to fill). To decrease latency, you might parallelize — but parallelization adds load (more requests at once, which can reduce throughput if the server is saturated). Every performance optimization is a tradeoff between these two axes.

---

## Evaluate

When someone says 'the system is slow,' ask: slow for whom? A single user seeing high latency? Or the system failing to handle throughput at peak? The fix is different. High latency for individual users might mean caching or CDN. Low throughput at peak might mean horizontal scaling or load balancing. Diagnosing the right problem requires knowing which axis is broken.

---

## Create

Design a system for ordering coffee. Who's the client? Who's the server? What's the request-response pair? What's the latency budget (how long will customers wait)? What's the throughput requirement (how many customers per hour)? What tradeoffs would you make to hit both?

---

## A common misconception

**'Latency and throughput are the same thing.'** They're not. A system can have low latency (each request is fast) but low throughput (it can only handle a few requests at once). Or high throughput (handles many requests) but high latency (each one takes a while). Confusing them leads to optimizing the wrong thing.
