# Six Words That Unlock Everything

Every craft has its foundational vocabulary. Cooking has *salt, fat, acid, heat*. Music has *melody, harmony, rhythm, timbre*. System design has its own six — and once you own them, every conversation about AI architecture stops sounding like a foreign language.

These aren't just definitions to memorize. They're the conceptual tools you'll use to reason about every system in this curriculum. A senior engineer doesn't think "what is latency?" — they think "the p99 latency of this API is 200ms, which means the user perceives it as instant." The words become instinct.

---

## Remember — name it

The six words, with real numbers:

- **Client** — the asker. Your browser, your phone app. Sends requests.
- **Server** — the answerer. A computer in a data center. Receives requests, sends responses.
- **Request** — one question from client to server. Measured in bytes and milliseconds.
- **Response** — the server's answer. Also measured in bytes and milliseconds.
- **Latency** — how long one request takes. Measured in milliseconds (ms). Under 100ms feels instant. 100-1000ms feels responsive. 1-2s feels slow. 5s+ feels broken. (Based on Jakob Nielsen's 1993 research, still valid.)
- **Throughput** — how many requests per second (RPS) the system handles. A single web server: 1,000-10,000 RPS. A load-balanced cluster: 100,000+ RPS. PostgreSQL: 10,000+ simple queries/second.

Two more that complete the kit: **scaling** (making the system handle more load) and **tradeoff** (the central act — you can't have everything).

---

## Understand — explain it in plain words

**Client and server.** The asker and the answerer. Your browser is a client. The computer in a data center answering its requests is a server. In a restaurant: you're the client, the kitchen is the server. This seems simple, but the distinction matters because it determines who initiates communication (the client) and who responds (the server). Modern systems blur this — a service can be both a server (to its callers) and a client (to the services it calls) — but the roles are always clear at any given moment.

**Request and response.** The atomic unit of all client-server communication. One question, one answer. Everything else is built on this. When you load a webpage, your browser makes dozens of request-response pairs: one for the HTML, one for each CSS file, one for each image, one for each API call. A typical web page makes 50-100 requests. Understanding this lets you reason about *what* a system is doing at any moment.

**Latency vs. throughput.** The two axes of performance, often confused. *Latency* is how long one request takes, measured in milliseconds. *Throughput* is how many requests happen per unit of time, measured in requests per second. They're related but not the same. A kitchen that handles 1,000 orders an hour but each takes 45 minutes has high throughput, high latency. A kitchen that handles 10 orders an hour but each takes 5 minutes has low throughput, low latency. You can optimize one and hurt the other — adding more chefs increases throughput but if they get in each other's way, latency per dish can increase. This is why performance engineering is a distinct skill.

**Scaling.** Making a system handle more load. *Vertical scaling* = buy a bigger server (more CPU, more RAM, faster disks). One chef who's really fast. Limited by hardware — you can't buy an infinitely big server, and the biggest servers are expensive. *Horizontal scaling* = add more servers (more instances behind a load balancer). Twenty regular chefs. Cheaper and more reliable (if one server dies, the others keep going), but harder to design for — because now your servers need to coordinate, and coordination is where distributed systems get complex. Stateful services (databases) are hard to scale horizontally; stateless services (API servers) are easy. This is why modern architecture separates state (in databases) from compute (in stateless services).

**Tradeoffs.** The central act. You can't have everything — fast, cheap, reliable, pick two. Every design decision gives something up. System design is the art of choosing which things to give up. A system that's perfectly reliable is expensive (triple redundancy, multi-region). A system that's cheap is less reliable (single instance, no backup). A system that's fast might sacrifice consistency for speed (eventual consistency vs. strong consistency). There are no solutions, only tradeoffs. This is the most important word in the entire curriculum.

## Apply — use it on a real system

Take any app you used today. Identify:
1. The client (your phone? your browser?)
2. The server (where is it running? AWS? GCP? A data center?)
3. One request-response pair you triggered (tapping a button → seeing a result)
4. Estimate the latency (did it feel instant, or laggy?)
5. Estimate the throughput requirement (how many users at peak?)

For a food delivery app at Friday 7pm:
- Client: your phone (iOS/Android app)
- Server: AWS, multiple regions
- Request: "place order" → response: "order confirmed"
- Latency: should be under 2 seconds (or users abandon)
- Throughput: 10,000+ concurrent orders in a major city

For an LLM chatbot:
- Client: your browser (web app)
- Server: Anthropic/OpenAI API, or self-hosted on GPU
- Request: "How do I reset my password?" → response: generated text
- Latency: 500-3000ms (LLM generation is slow)
- Throughput: 100-1000 concurrent users (limited by GPU capacity or API rate limits)

This exercise makes the vocabulary concrete.

## Analyze — where latency and throughput conflict

Latency and throughput are in tension. To increase throughput, you might batch requests — but batching adds latency (you wait for the batch to fill before sending). To decrease latency, you might parallelize — but parallelization adds load (more requests at once, which can reduce throughput if the server is saturated). Every performance optimization is a tradeoff between these two axes.

Example: A payment processor handles 100 transactions/second with 500ms latency. To handle 1,000/second, you could:
- Add more servers (horizontal scaling) — throughput 10x, latency unchanged
- Batch transactions (process 10 at a time) — throughput 10x, latency +200ms (waiting for batch)
- Use a faster database (vertical scaling) — throughput 2x, latency -100ms

Each option has different cost, complexity, and tradeoffs. The right choice depends on whether your users care more about latency (real-time bidding: 10ms budget) or throughput (batch processing: latency doesn't matter, throughput is everything).

## Evaluate — diagnose the right problem

When someone says "the system is slow," ask: slow for whom? A single user seeing high latency? Or the system failing to handle throughput at peak? The fix is different. High latency for individual users might mean caching or CDN. Low throughput at peak might mean horizontal scaling or load balancing. Diagnosing the right problem requires knowing which axis is broken.

A common mistake: optimizing latency when the problem is throughput. "The API is slow" might mean "p99 latency is 2 seconds" (fix: caching, faster database, async processing) or "the server is rejecting 30% of requests at peak" (fix: more servers, better load balancing). Different problems, different fixes.

The p99 latency metric matters more than average latency. If average latency is 200ms but p99 is 3 seconds, 1% of your users are having a terrible experience. Always measure percentiles (p50, p95, p99), not just averages. Averages hide outliers; percentiles reveal them.

## Create — design a coffee ordering system

Design a system for ordering coffee. Who's the client? Who's the server? What's the request-response pair? What's the latency budget (how long will customers wait)? What's the throughput requirement (how many customers per hour)? What tradeoffs would you make to hit both?

Consider:
- Peak hours (7-9am): 200 customers/hour, each waits <60 seconds
- Off-peak: 20 customers/hour, each waits <2 minutes
- Payment: synchronous (wait for card) or async (pre-order, pay later)?
- Mobile ordering: does it change the architecture?

The key insight: the system has two modes (peak and off-peak) with very different requirements. A system designed for peak (200/hour, 60s) is over-engineered for off-peak. A system designed for off-peak (20/hour, 2min) will fail at peak. You need elasticity — the ability to scale up for peak and down for off-peak. This is why cloud computing (AWS, GCP) exists: you pay for what you use, not for peak capacity.

---

## A common misconception

**"Latency and throughput are the same thing."** They're not. A system can have low latency (each request is fast) but low throughput (it can only handle a few requests at once). Or high throughput (handles many requests) but high latency (each one takes a while). Confusing them leads to optimizing the wrong thing — adding more servers when the problem is database query speed, or optimizing queries when the problem is not enough servers.
