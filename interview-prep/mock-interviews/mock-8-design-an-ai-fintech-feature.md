# Mock 8 — Design an AI Feature for a Fintech App

## The prompt

"A consumer fintech app (15M users, banking + budgeting) wants an AI assistant: 'ask anything about your money.' The CPO wants transaction Q&A ('how much did I spend on coffee in March?'), insights ('am I saving enough?"), and general chat. Regulators, fraud teams, and the CEO all have opinions. Design it — and design what you'd refuse to build."

*45 minutes, paper, timer.*

---

## Candidate-quality walkthrough

**[0:00–5:00 Clarify]** "Three scoping questions decide the architecture. (1) What's the *data boundary* — can transactions leave our perimeter to a model provider, or is this on-prem/deployed-in-VPC territory? (2) What's the *action boundary* — does the assistant ever DO things (move money, cancel subscriptions) or only inform? (3) What's the regulatory frame — who audits this, and what's the process when it's wrong?" Interviewer: data can go to a major provider under DPA but no raw PII in prompts if avoidable; actions are v2, inform-only for launch; auditors will want explanations; 'the CEO wants vision, the risk team wants a shrink ray.'

**[5:00–10:00 Estimate]** "15M users, realistic assistant adoption ~10–20% at 3 questions/week ≈ 5–8M queries/month ≈ 3 QPS mean, 20–40 peak — small load, so my constraints are compliance and correctness, not scale. Cost at ~3K tokens/query mostly on-prem-ish small/mid models + heavy pre-computation: $2–8K/month — cheap. The expensive part is the *feature store of financial aggregates* (per-category-per-month spends, trends) — that's precomputed batch, not LLM, and it makes answers fast, cheap, AND auditable."

**[10:00–20:00 High-level]** The insight that shapes everything: **most 'AI assistant' questions are database queries wearing conversational clothes.** So: intent router → (a) **structured path**: transaction/aggregation questions → semantic parser → validated SQL/feature lookups over the user's own data (parameterized, allowlisted tables, row-limits) → template + LLM phrasing of *verified numbers* → cited answer; (b) **knowledge path**: product/financial-literacy questions → RAG over internal KB (compliance-approved content) with citations; (c) **refusal path**: predictions ("will I be able to afford…"), tax advice, anything advisory → scripted boundaries + human channel. Agentic free-form tool use is NOT in v1 — the query surface is three typed paths, each auditable. Privacy: per-user aggregation means prompts contain (category, month, amount) tuples — tokenized, non-identifying — not raw transaction text; the semantic parser runs on-prem; PII scrubbing at every boundary; per-user data isolation is the *session key*, not a prompt instruction (cap2's lesson: isolation is enforced by architecture)."

**[20:00–35:00 Deep dive — interviewer picks wrongness, regulation, and the refuse-list]** "Wrongness in fintech has a specific shape: a *confidently wrong number* — 'you spent $212' when it was $120 — which destroys trust instantly and generates support tickets with screenshots. So numbers are NEVER generated: the structured path computes them deterministically and the LLM only phrases them (b7's pattern: the model as a UI over verified data, not as a source of facts). Hallucination surface shrinks to phrasing; faithfulness eval targets the *relationship* between phrasing and the computed values. Evaluation: golden set of 200 canonical questions with verified answers (regression-tested on every model/prompt change — my b4 gates), adversarial set (ambiguous date ranges, empty months, users with 3 transactions), and a *numeric-parity check* — the answer's numbers must match the computed payload exactly, enforced in code. Regulation: the audit package = intent-classification logs, the exact query+payload per answer, model/prompt versions, and the refusal boundary policy — every answer reconstructible. The refuse-list, said plainly: no personalized investment advice (regulated activity), no tax conclusions (refer a professional), no predictions of affordability phrased as fact, no executing anything in v1, and no sentiment-laden judgments about the user's spending ('you waste too much on coffee') — insights are descriptive, not moralizing, which is partly a product-values decision and I'd want it written down."

**[35:00–40:00 Tradeoffs]** "What I gave up: free-form agent autonomy (the demo-magic version — 12 tools, wandering loops — fails every audit conversation; typed paths trade magic for defensibility); frontier models on raw transaction text (privacy + cost + the deterministic-path insight makes it unnecessary); and 'general chat' (v1 refuses it — the assistant is *about your money*, which is also a trust signal: scope discipline). At 10× usage: the precompute layer scales batch-style, the parser scales cheaply, nothing changes structurally — the design is flat-cost by construction."

**[40:00–45:00 Operate]** "Dashboards: intent-mix (structured vs. knowledge vs. refusal — watch refusal drift), numeric-parity violations (target: zero, alert on any), latency by path, containment (questions answered vs. escalated), complaint rate (the real trust metric), and per-path eval scores trending. Rollout: internal users → 1% → 10% → full, with the compliance sign-off gates at each step and the refusal-path battle-tested by a red team before launch. Riskiest assumption: that the intent router is reliable enough — the router confusion matrix IS the launch gate (a 'how much did I spend' question hitting the knowledge path is a wrong answer in waiting)."

## The curveballs

- "The CEO wants 'AI insights that tell users they're overspending on subscriptions.'" → "Descriptive, yes — 'subscriptions rose 22% in 3 months' with the data; judgmental framing, no. The product-values line I drew at [35:00] is also a retention argument — apps that nag get silenced. If leadership insists on judgment, it's A/B-tested against churn with the same rigor as anything else."
- "A regulator asks how the assistant decides what to say. Walk them through one answer's life." → "Full replay from the audit log: your question, intent classification (score + threshold), the validated query, the computed payload, the prompt version, the generated phrasing, the parity check. Every number traceable to a row; every path versioned. That's what 'auditable AI' means — and why the free-form-agent version couldn't pass this conversation."
- "Users type their SSN into the chat. Now what?" → "Input-layer PII detection (regex + NER classifier) → the message never reaches the model; user gets an immediate 'please don't share that' + the incident logged for security review (FN-style: detection is a layer, not a hope). Logging captures the *event*, not the digits."
- "Fraud team wants to use the assistant's session as an anti-fraud signal." → "Interesting and dangerous: query patterns as fraud signals ('what's my balance' from a new device at 3AM) — legitimate, IF consent language covers it and the assistant isn't the only fraud surface. I'd route it through the existing fraud feature pipeline (A.5's layered rules), not build it into the assistant itself. Scope discipline, again."

## Scoring rubric (condensed)

Strong-hire: the structured-path insight (LLM phrases verified numbers, never generates them); typed paths over free-form agents *argued from auditability*; the refuse-list stated with reasons; privacy as architecture (scrubbing, isolation by session); numeric-parity as a code-level check. Weak: RAG over transactions; agent-with-tools demos; "add a disclaimer" for regulatory questions; no refuse-list.

**The hire-line:** regulated-domain AI is a *scope* interview. The winning sentence is almost always a refusal — "here's what we won't build and why" — delivered with mechanisms, not fear.
